# S24.1 — Destiny Proposal Persistence

**Status:** Implemented · Feature flags inherit S23  
**Package:** `@wingman/destiny-v2` (`DestinyProposalStore`, `RedisDestinyProposalStore`)  
**Related:** [`S23_DESTINY_V2.md`](./S23_DESTINY_V2.md), [`V1.1_ADVANCED_ENGINE.md`](./V1.1_ADVANCED_ENGINE.md)

## Rule

> Destiny proposals are short-lived consent objects. Persist them in **Redis / shared ephemeral store**, not Postgres protocol hydrate. Never auto-match; MUTUAL still hands off to immutable V1 Signal → Connection.

```text
Nest A / Nest B
      │
      ▼
DestinyProposalStore (Memory | Redis)
      │
      ├── proposal:{id} + user/pair indexes
      └── accept lock: destiny-accept:{id} (EphemeralStore)
```

## Flags / config

| Env | Effect |
|-----|--------|
| `DESTINY_V2_*` | Unchanged from S23 |
| `REDIS_URL` | When set, Nest builds `RedisDestinyProposalStore` (unless overridden) |
| `DESTINY_V2_STORE=memory` | Force process-local store even if Redis is configured |

## Behavior

- `DestinyProposalStore` is **async** so memory and Redis share one engine API.
- Redis wire format serializes `acceptedBy` as an array and dates as ISO.
- Open proposals index by pair (`activePair`) and user sets; TTL follows `expiresAt` (terminal rows kept briefly for handoff reconcile).
- Multi-instance accept: shared store + ephemeral lock; only the lock holder creates the V1 Signal/Connection; peers wait for `connectionId` on the shared proposal.
- Cooldown ledger remains process-local in this sprint (proposal sharing is the named S24.1 gate).

## Gates

Verified by package tests + `apps/api/src/s24.1.destiny-persistence.test.ts`:

- Shared store visible across two Nest instances
- Consent on instance A readable on instance B → MUTUAL handoff once
- Flag OFF does not write proposals
- Domain still has no `@wingman/destiny-v2` import
- Not stored in Postgres/`ProtocolRepository`

## Out of scope
